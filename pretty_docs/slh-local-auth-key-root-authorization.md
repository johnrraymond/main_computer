# ORG-SLH LOCAL-AUTH-KEY — Local Root Authorization Contract

**Status:** V6-A implements the **ORG-SLH root file and root-authorized administrator-grant API**. V6-B implements **explicit LMS-SLH root consumption and identity registration** through its local API. V6-C connects the existing MCEL **Login Administrator** action to conditional first-administrator registration. On a truly unestablished organization, the same **Login Administrator** click now runs the existing protected one-time `bootstrap.secret` P-256 initialization with the selected identity, configures a loopback TLS listener when configuration is genuinely absent, activates ORG-SLH, and signs in. `/v1/bootstrap/recovery` remains a stub.

## Objective and trust model

The **ORG-SLH Organization Service** owns one durable `LOCAL-AUTH-KEY` for its organization authority. The **LMS-SLH Local Management Service** can read that key directly from the same host's protected disk and present it to ORG-SLH to authorize **explicit identity enrollment with administrator permissions**, including initial setup and recovery when an earlier administrator's private key is gone. The user chooses **any ordinary LMS-SLH identity**, including a generated generic-slug identity. No cryptographic identity is inherently an administrator; ORG-SLH grants and verifies the role.

**Phase assumption:** The machine hosting ORG-SLH and its operating-system access controls are trusted. A locally authorized LMS-SLH process can read the key on disk. This phase **does not** require a hardware security module, an additional recovery authority, or a loopback-only ORG-SLH administration endpoint. It does require that key files are not exposed to an untrusted account, browser, log, diagnostic or source repository.

The root key is a **bearer capability**. **Possession of it authorizes its defined root operations even when the request originates remotely.** Calling the credential `LOCAL` describes where it is normally kept and obtained, **not a network-origin restriction**. A remotely reachable ORG-SLH API must enforce the same root verification as a local caller. Treat exfiltration as compromise of root administrative authorization; host security is a deliberate assumption, not a cryptographic guarantee of locality.

## Ownership and startup lifecycle

1. **ORG-SLH startup (V6-A implemented):** Before accepting root-authorized operations, inspect the persistent root-key file. If it is genuinely absent, generate a high-entropy random `LOCAL-AUTH-KEY` and atomically persist it to the ORG-SLH state directory. If valid material exists, **reuse its exact value on every restart**. An unreadable, malformed or conflicting existing file is an explicit error; never silently overwrite it. Concurrent startups must not mint competing keys. The root can exist with no active administrator. In V6-A it is created as the ORG-SLH process starts after its existing organization-setup and explicit-enable gates; LMS-SLH startup alone does not create it.
2. **Key custody:** ORG-SLH owns the file and validator; LMS-SLH has authorized read access to that **same** protected file. No separate LMS-SLH copy, second key authority, key-export API or browser-side storage is necessary. A truly missing file at startup triggers creation by ORG-SLH under this contract; it does **not** remove existing organization records or automatically change enrolled administrators. Losing an existing key means losing the old bearer root even if a new one is generated: protect the file and its backups appropriately.
3. **Separate credentials:** `LOCAL-AUTH-KEY` is **not** an LMS-SLH identity private key, the ORG-SLH service signing/TLS key, an identity fingerprint, a session bearer, a marketplace/wallet key, a one-time enrollment invitation, or the current one-use `bootstrap.secret`. Those credentials have different duties and lifetimes.
4. **No silent launch:** LMS-SLH starting does not itself start ORG-SLH or enroll an administrator. ORG-SLH initializes the root when **that service** starts; on this Windows development machine, neither service is configured to start at Windows boot as a side effect of this contract.

## Root-authorized enrollment and recovery

1. The operator selects an **existing or newly created ordinary identity** from LMS-SLH (for example, `734-CXR-SD-104-EU-26-11-09`). Its slug, description and default status convey **no organizational privilege**.
2. LMS-SLH reads the ORG-SLH-owned `LOCAL-AUTH-KEY` on the trusted host. In a deliberate registration/recovery action, the trusted server-side LMS-SLH adapter transmits it to the intended ORG-SLH API **over authenticated encrypted transport**. A remote API is permitted; the key is never sent to browser JavaScript or added to a URL, console, access log or persisted HTTP trace. The receiving service must be authenticated so the root is not handed to an impersonator.
3. ORG-SLH verifies the supplied root key against its persisted root, and verifies **proof of possession** of the selected identity's private signing key using the ordinary LMS-SLH signing path and a fresh, operation-bound challenge. A public key or arbitrary identity ID by itself is insufficient.
4. Upon valid root authorization **and** key-possession proof, ORG-SLH durably enrolls the public identity and assigns the administrator role through its normal registry/authorization model. The operation is explicit, auditable, scoped to the intended organization and selected identity, and idempotent under retry; it does not issue a privileged session to an unrelated identity.
5. The identity subsequently authenticates through the **normal challenge/signature/session protocol**, with the ORG-SLH enrollment and role checks. It **does not present `LOCAL-AUTH-KEY` for ordinary requests**.
6. The same root-authorized grant can restore administration after an earlier administrator key is lost. **Do not reset the organization, rename or replace an existing identity key, or automatically revoke the old administrator.** Verify login and authority of the newly enrolled identity first; retirement/revocation is a subsequent, explicit operation.

**Normal administrator-approved enrollment remains valid.** The root path is the local-operator bootstrap/recovery/administrative-authorization alternative, not a replacement for challenge-based identity authentication, normal administrator approvals, scoped policy, or revocation.

## Implemented V6-A wire and storage contract

- ORG-SLH stores a 48-random-byte URL-safe bearer root (64 text characters) in its protected state file `LOCAL-AUTH-KEY`. It generates the file exclusively if absent on ORG-SLH process startup, otherwise validates/reuses it. Invalid or unreadable material stops startup. The file is **not** generated by LMS-SLH startup.
- The network-facing **TLS-only** ORG-SLH operation is `POST /v1/admin/root/identities`, with `Authorization: Bearer <LOCAL-AUTH-KEY>` and a JSON object containing `device_id`, `public_key`, `client_nonce`, `issued_at`, and `proof` (base64url P-256 ECDSA signature). The route is unavailable on the plaintext LMS-SLH listener. An optional signed `bootstrap_only: true` constraint requires that ORG-SLH have zero active administrator identities at the moment the grant commits. Omission preserves the existing explicit recovery grant.
- The signed canonical object is `{"version":1,"action":"slh.admin.root.register","audience":"slh://" + ORG_service_signing_fingerprint,"device_id":...,"public_key":...,"client_nonce":...,"issued_at":...}` for explicit grants; automatic first-admin grants also include `"bootstrap_only":true` in the signed statement and submitted request. The fingerprint here identifies the existing ORG-SLH P-256 **service signing identity**, not the TLS certificate. `issued_at` is Unix seconds and must be within 120 seconds; the random URL-safe nonce must be at least 24 characters. Nonces are durably replay-checked across service restarts.
- On authorization, the service atomically creates an ordinary P-256 device enrollment with `admin` **role**, without creating any new private key, granting a session, revoking existing identities or resetting organization state. Exact repeated registration of the same active administrator returns `ALREADY_REGISTERED`; conflicting ID/key enrollments fail.
- Responses and audits contain public identity metadata only. Wrong root is `LOCAL_AUTH_KEY_DENIED`; wrong signature `INVALID_KEY_PROOF`; stale signed proof `ROOT_PROOF_EXPIRED`; replay `ROOT_PROOF_REPLAY`. A root grant is not an ordinary login.
- **Implemented in V6-B:** An explicit `POST /v1/local/organization/admin/identities` on the LMS-SLH loopback management API, accepting `{"device_id":"..."}` for deliberate root-authorized registration and `{"device_id":"...","bootstrap_only":true}` for the constrained first-admin login path. LMS-SLH retrieves the selected identity and signs the precise V6-A proof through its existing Authenticator API, reads ORG-SLH's persistent root from disk, verifies ORG-SLH's installed TLS leaf pin before sending the bearer, then returns only the public grant receipt (`status`, `device_id`, `fingerprint`, `role`). It never creates a root or changes the default identity. The existing ORG organization must be established, enabled and running.
- **Login Administrator, fresh organization:** When LMS-SLH observes `initialized=false` and administrator state `NOT_ESTABLISHED`, the click performs the existing **local, protected one-time P-256 bootstrap** with the selected ordinary identity (no admin-name/ID/P256 form), configures an otherwise unconfigured ORG-SLH listener at `127.0.0.1` using default ports, activates the service, then performs a normal signed login. Any existing configured binding is preserved. Root-grant enrollment is **not** used before organization initialization; the separate `bootstrap.secret` still guards this first setup. Neither LMS-SLH startup nor a status read performs the bootstrap or launches ORG-SLH.
- **Login Administrator, established organization (V6-C):** LMS-SLH reads local ORG-SLH administrator state without querying a network endpoint. If an established, running organization has zero active administrator devices (`MISSING` or `NO_ACTIVE_DEVICE`), the click sends a signed `bootstrap_only: true` root grant, and ORG-SLH checks the zero-admin condition atomically before normal login. With any existing active administrator, login cannot promote a different identity. Missing, revoked or inconsistent authority never authorizes a new first-administrator grant.
- **Atomic guard:** For `bootstrap_only: true`, the selected identity signs that constraint as part of the root-registration proof. ORG-SLH checks again inside the database write transaction, refusing a new automatic grant if any active administrator identity exists. The existing explicit root-authorized registration API without this flag remains available for deliberate recovery, independent of login.
- **Not yet supplied:** Fresh-organization creation/configuration without the legacy first-bootstrap requirement, and a distinct MCEL recovery control when an existing administrator's key is lost.

## Acceptance criteria for the implementation patch

- New ORG-SLH state generates a root once at service startup; subsequent restarts return the same root; concurrent start cannot create divergent roots.
- Existing valid root is reused; malformed/inaccessible/conflicting state fails without overwriting; key bytes never appear in status, API discovery, UI, diagnostics or logs.
- LMS-SLH can read the ORG-SLH key from the host's authorized disk location and cannot manufacture a valid key on behalf of ORG-SLH.
- An ordinary LMS-SLH identity proves possession and obtains an explicit `admin` grant only with the correct root; wrong root, wrong target, replay, changed public key or invalid signature is rejected.
- Root-authorized requests are **not restricted by source loopback address**; authenticated encrypted transport protects transmission even when the ORG-SLH API is network reachable. Theft of the root remains sufficient to attempt root-authorized operations under the phase's trusted-host assumption.
- Both initial registration and later recovery work without an already authenticated administrator. Existing organization data, all other identities and roles remain unchanged unless explicitly authorized.
- After enrollment, normal challenge/login succeeds without supplying the root; unregistered identities cannot log in as administrators.
- No ORG-SLH activation merely from LMS-SLH startup, no Windows boot task, **startup-triggered** administrator grant, silent administrator revocation, or new identity type. An explicit first **Login Administrator** click is permitted to activate the newly established organization on loopback. An explicit **Login Administrator** click is allowed to grant the *first* active administrator only; it cannot increase an existing administrator set.

**Implementation boundary:** V6-A, V6-B and V6-C implement ORG-SLH root authorization, LMS-SLH consumption, and **conditional first-administrator enrollment when Login Administrator is clicked**. A fresh organization uses the existing guarded one-time bootstrap automatically from that click, followed by loopback-first configuration, activation, and signed login. An established running organization with zero active administrators uses the signed root-grant path instead. Neither action is triggered by service startup or identity discovery. The generic `/v1/bootstrap/recovery` route remains unimplemented; the new root grant handles recovery of administrator access in an established organization.
